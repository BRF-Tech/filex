# MCP OAuth Implementation Plan

> **For agentic workers:** Use executing-plans for the sequential implementation; the independent SQL record adapter is delegated under dispatching-parallel-agents.

**Goal:** OAuth-only MCP clients connect by URL and browser sign-in without custom headers.

**Architecture:** Broker the existing filex browser identity into MCP-bound, scoped API tokens. Persist clients, pending consent, authorization codes and rotating refresh credentials through shared SQL operations; leave the existing MCP authorization pipeline in place.

**Tech Stack:** Go net/http, chi, existing auth/db/APIToken services, Vue login return navigation.

**Spec:** ../specs/2026-11-20-mcp-oauth-design.md

## Global Constraints

- No production deployment, push or changes to Pocket ID.
- Preserve existing API-token clients and live account/tenant/file permission enforcement.
- S256 PKCE, exact registered callback, resource binding, single-use codes, consent CSRF protection and hashed credentials are required.

## Review Focus

- Discovery at root and prefixed deployments must identify the actual MCP resource.
- A wrong verifier, client, redirect, resource or expired/replayed code must mint nothing.
- Refresh/revocation must remain atomic and honor disabled users and revoked grants.
- Unauthenticated or token-authenticated requests must never consent as a browser user.
- OAuth access tokens must not become general-purpose filex API/admin credentials.
